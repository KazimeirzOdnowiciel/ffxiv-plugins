# Patch-day runbook: the obtain snapshot

The plugin ships one generated file, `src/Mountbook/Data/mount-sources.json` (patch, whistle item,
community ownership, tradeable/music flags, and the "How to obtain" lines for every mount the site
lists), and the data work around it is supported by one other generated file outside the repository,
the model map at `D:\Deepseek\tools\mdlrip\out\mount-model-map.csv`. **Both are stale the day the game
adds mounts**, and neither is regenerated by a build. This is the order to refresh them in, and the one
command that proves the new snapshot before it is committed.

Run this on a patch day, or when ffxivcollect corrects a mount's sources or patch value. It is not part
of a UI change: a feature pass never regenerates the dataset.

Order: **regenerate and validate -> read the report -> goldens -> build/tests/format -> changelog +
version -> `build.ps1` -> commit (`dist/` + `repo.json` with the bump) -> check in the client -> record
the run.**

## 0. Prerequisites

- The .NET 10 SDK, and the game installed at `D:\ff14\SquareEnix\FINAL FANTASY XIV - A Realm Reborn`
  (the model map reads the game's own sqpack; nothing else here needs the game).
- `D:\Deepseek\tools\mdlrip` built once (`dotnet build -c Release`).
- Network access to `ffxivcollect.com` (the generator's only source).

## 1. Refresh the model map (the sheet export)

The model map is one row per `Mount` sheet row - id, name, model path, whether the file exists - so it
doubles as the "what is a mount in this game build" list the validator checks ids against.

```powershell
cd D:\Deepseek\tools\mdlrip
dotnet run -c Release -- --resolve
```

Expect `wrote ...\out\mount-model-map.csv` and three counts: `demihuman/exists`, `monster/exists`,
`placeholder/missing`. On 2026-11-01 they were `33 / 400 / 17`, for 450 rows. **A different total is the
patch's new mounts** - note it, because step 2's `mount-added` note should agree with it.

## 2. One command: regenerate and validate

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File src/Mountbook/tools/patch-day.ps1
```

It does five things, in this order, and stops at the first problem:

1. copies the committed snapshot aside as the **baseline** (the only reference that can answer "what
   changed");
2. regenerates a **candidate** from ffxivcollect into a scratch file - the committed file is not
   touched yet;
3. converts the model map's `mount_id` column into the **sheet ids** the validator wants;
4. runs `src/Mountbook.Tools` (the same `Services/` code the plugin and its tests compile) over the
   candidate, the baseline and the sheet ids;
5. **only when there are no errors** copies the candidate over
   `src/Mountbook/Data/mount-sources.json`.

A failed run leaves the working tree exactly as it was, prints the findings, and keeps the rejected
candidate in its scratch directory for inspection. The report is also written as markdown to
`artifacts/patch-day/validation-<stamp>.md` (git-ignored - paste it into the commit message or PR).

| flag | use |
| --- | --- |
| `-NoWrite` | validate a regeneration and change nothing: a rehearsal, or a check on CI |
| `-SkipRegenerate` | validate the committed file as it stands; no network |
| `-SkipSheet` | skip the Mount sheet ids check (offline, or no model map) |
| `-SheetIds <file>` | the sheet ids from somewhere else: one id per line, or a model map CSV |
| `-ModelMap <file>` | a different model map (default: the `tools/mdlrip` copy) |
| `-ReportPath <file>` | where the markdown report goes |
| `-AllowedShrink/-AllowedGrowth/-Minimum` | widen the row band deliberately (see `row-count`) |

The script warns when the model map **predates the snapshot's `generated` date** (not the snapshot
file's timestamp - git checks every file out "now", so a fresh clone would call a fresh map stale): an
old map cannot know the patch's new mounts, and would pass a mount the game has not published.

## 3. Read the report

Errors block; warnings are changes a human has to read and accept; notes are context. Every finding
carries a code, and the code is what the table below is for.

| code | severity | what it means | what to do |
| --- | --- | --- | --- |
| `row-count` | error | the row count left the band: the committed count minus 8 to plus 40, never below 300 | a drop is a partial fetch or a changed endpoint - rerun; if it repeats, look at the API response before touching the generator |
| `unknown-mount-id` | error | an id is not a row in the game's `Mount` sheet | the site invented an id, or the model map is stale (step 1). Never ship it: the plugin would look up a mount the game does not have |
| `mount-disappeared` | error | a mount the committed snapshot had is gone | the game does not remove mounts. A partial fetch, or a query that now filters differently |
| `sources-lost` | error | a mount that had "How to obtain" lines now has none | read the site's record for that mount; an empty list is worse than a stale one. If the site really dropped it, edit the generator or fix the site's data first |
| `patch-missing` | error | a mount has no patch value | same: the patch filter and the expansion strip cannot place it |
| `patch-not-in-sheet` | error | a patch value maps to no expansion the plugin ships (e.g. the first `8.0` mount) | add the expansion to `MountBreakdown.Expansions` **and** `MountExpansion` deliberately, in a separate commit, then rerun. Otherwise every new mount lands in "Other" |
| `patch-changed` | warning | an existing mount's patch value moved | read them; the site sometimes corrects a patch. Say so in the changelog |
| `patch-added` | note | a patch label nobody has seen before | expected on a patch day; check the label is a real patch number and not a typo |
| `mount-added` | note | mounts the committed snapshot did not have | expected on a patch day; cross-check the count against step 1 |
| `ownership-drift` | note | community ownership percentages moved | the site recounts daily. This is why a regeneration's diff is never empty - it is not the patch's data change |
| `sheet-coverage` | note | how many `Mount` sheet rows have no obtain data | expected (unavailable mounts and the unnamed placeholder rows) |
| `sheet-skipped` | note | no sheet ids were supplied | the ids were only checked for shape. Rerun with the model map before shipping |

The validator judges whether the snapshot can be described honestly. It cannot judge whether the site's
data is *right*, and it cannot see a `Mount` sheet column being renamed (that is the API audit's job) or
a new localisation of a source type.

## 4. Goldens

A data-only change must move nothing on screen:

```powershell
dotnet build src/Mountbook.Previews/Mountbook.Previews.csproj -c Release
~/.dotnet/tools/glasswork-preview.exe --assembly src/Mountbook.Previews/bin/Release/Mountbook.Previews.dll --compare src/Mountbook.Previews/goldens --out artifacts/previews/Mountbook
```

Expect `every image matches its golden` (10 scenes in the committed tree - the count is whatever the
preview assembly defines, so read the table, not this number). `--out` is not optional: without it the tool prints
its help and exits 0, which reads exactly like a pass. **If a scene moved, look at
`artifacts/previews/Mountbook/<scene>.png` and its `.diff.png` before regenerating anything** - a moved
golden after a data change means a source line or a patch value that a scene draws changed, and that is
a finding, not a re-baseline. Regenerate with `--update` only after you have looked and decided.

## 5. Build, tests, format

```powershell
dotnet build src/Mountbook/Mountbook.csproj -c Release                        # 0 warnings
dotnet run --project src/Mountbook.Tests/Mountbook.Tests.csproj -c Release    # quote your run, not this
dotnet format src/Mountbook/Mountbook.csproj --verify-no-changes              # clean
```

The dataset test (`MountSourcesDataTests`) parses the committed file exactly as the plugin does, and
`MountSourcesValidationTests` pins every rule above; both fail on a bad regeneration, so this step is
not a formality after step 2.

## 6. Changelog and version

- Write the changelog entry for the version being bumped (see the CHANGELOG task's format: what a
  player notices, one line per change - "the 7.6 mounts are in, and their obtain steps").
- Bump `<Version>` in `src/Mountbook/Mountbook.csproj` (it becomes the manifest's `AssemblyVersion`,
  which is what the installer compares). That property is the one place a version lives. **The bump is what makes
  the release workflow publish** - the workflow refuses to commit artifacts without one.

## 7. Package

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
```

It rebuilds every listed plugin, copies each `latest.zip` into `dist/` and rewrites `repo.json`. `build.ps1`
repackages *every* plugin, so the other `dist/*.zip` files come back modified: `git checkout --` those and
commit only Mountbook's zip, its icon and the regenerated `repo.json`. `repo.json`'s `LastUpdate` is
generated output - do not hand-edit it back. The zip's name is the version, so a bump to `1.0.0.0` has to
produce `dist/Mountbook-1.0.0.0.zip` and `dist/icons/Mountbook-1.0.0.0.png` - if the name still carries the
old version, the `<Version>` edit did not reach the build. The superseded zip may stay in `dist/` (old
download links keep working, and nothing in `repo.json` points at it any more).

## 8. Commit

One commit with: the regenerated `Data/mount-sources.json`, the changelog entry, the `<Version>` bump,
`dist/Mountbook-<version>.zip`, `dist/icons/Mountbook-<version>.png` and `repo.json` - **together**, so the
index and the artifact can never disagree.

A push to `main` touching `src/**` runs `.github/workflows/release.yml`, which rebuilds and commits
`dist/` + `repo.json` itself when it sees a version bump. Committing them by hand is still correct (and
is what a rehearsal has to do); the workflow then finds nothing to change.

## 9. Check it in the client

The gate proves build, tests, format and goldens - not that the running plugin reads the new data:

1. `load_dev_plugin` with `src/Mountbook/bin/Release/Mountbook.dll`, then `/mountbook`.
2. `get_dalamud_log` (with a cursor) for a "mount source data" error - the catalog logs one line when the
   embedded resource is missing or unreadable, and nothing when the data is fine.
3. In the search box, `patch:7.6` (or whatever the patch added) should return the new mounts, and the
   expansion strip should count them in the right expansion.

Do not reload the plugin under a session that is running an unattended loop (a selling or gathering
automation) - and do not mistake "the game is busy" for "the data is broken". When the client cannot be
touched, the cheapest honest substitute is to prove the data reached the build: the Release assembly
carries the snapshot as an embedded resource, so `grep` the build for the snapshot's `generated` date and
one of its rows. That proves the file is in what ships; the client pass still has to happen before the
release gate.
